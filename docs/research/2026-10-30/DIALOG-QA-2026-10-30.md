## Three things the browser pass changed (a screenshot of markup could not have caught any of them)

1. **The sheet was not keyboard-modal.** `aria-modal="true"` made it modal to a screen reader while `Tab` walked straight onto the page behind it — visible only as a blurred backdrop, so a member could activate something they could not see. The handler now traps `Tab`/`Shift+Tab` across visible, enabled controls. (Found by writing the trap test first, then watching the count walk out.)
2. **A reason could ride along between the two sheets.** Storing one `reason` slot and clearing it in a `kind` effect is both wrong and rejected by `react-hooks/set-state-in-effect`. The reason is now keyed by the act (`reasons[kind]`), so a "delete every message" confirmation *cannot* carry an unmatch's reason — the harness pins that shape.
3. **The QA harness itself was lying.** Re-opening the sheet without unmounting left the previous selection in place, so the first "report branch" screenshot toggled the chip *off* and photographed the wrong state. `open()` now bumps a `key`, matching how the product actually behaves (`profile-view` unmounts on close). **A mislabelled screenshot looked exactly like a passing test** — the same class of failure as an assertion that can't fail.
4. The photos are taken at the **phone** viewport, before the desktop resize, and one mislabelled shot (a "desktop" PNG rendered at 390px) was caught and fixed.

## Two bugs in the QA layer itself, both found while writing the above

Recording these because they are the class of failure that makes a green suite meaningless:

* `!/^0px none/.test(outline)` **passed on `outline: 3px none`** — a style of `none` is no
  indicator whatever the width says. The check now reads `outlineStyle` and accepts either a
  `solid ≥2px` outline or a `box-shadow` spread `≥1.5px`, because this app legitimately uses both
  mechanisms (`.fb-cta:focus-visible` vs the app-wide `:where(…)` rule).
* `nums.map(Number)` on `"2px"` is `NaN`, which `JSON.stringify` writes as `null` — so a real 2px
  ring read as missing and a passing assertion looked like a failing one. `parseFloat` is the fix.
  A chip also needs ~320 ms to settle, since it animates and an immediate read catches a mid-flight
  `1.82px`.

**Known cosmetic gap, not fixed here:** the dialog's focus ring is gold (app-wide `:where()` rule)
while its buttons' is ember (`.fb-cta:focus-visible`). Aligning them means changing a rule every
focusable element in the product depends on, which is a separate decision, not something to slip
in through one dialog.

## Limits — read these before treating this as sign-off

* **Chromium only.** No Safari/WebKit, no iOS or Android WebView, so `backdrop-blur`, `font-variant` and safe-area handling on WebKit are unverified.
* **No screen reader pass.** `aria-modal`/`aria-labelledby` are asserted as *attributes*; VoiceOver/TalkBack announcement order, and whether they *confine* a virtual cursor, are untested. The trap is `preventScroll`-based and does not set `inert` on the background, so a click — not a Tab — can still reach the page behind (deliberate: the backdrop is the dismiss affordance, and it is inert while `busy`).
* **Mounted in the QA harness, not inside `/app/profile` after sign-in.** The parent wiring (`profile-view` → `POST /api/chat/unmatch` → route → DB) is pinned by `scripts/trust/harness.ts` `[20]` and the storage semantics by `scripts/qa/pg-migration-verify.sh`; no browser here ever made a network request — callbacks are recorded, nothing is fetched.
* Fonts fall back to system faces, so type metrics carry the caveat recorded in `VISUAL-QA-2026-10-30.json`.
* Reproduce: `npm run build` (needed for the emitted CSS), `npm run qa:build` equivalent — `node scripts/qa/build.mjs` — then `PLAYWRIGHT_BROWSERS_PATH=0 node scripts/qa/dialog-check.mjs`.
