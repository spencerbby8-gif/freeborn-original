# Suspension notice and access: unresolved release gate

The current `/api/security/check` checks the latest suspension by email and returns a verdict; the app shell calls it asynchronously **after rendering** and normally signs the client out when `suspended` is true. It is not a server-wide authorization gate: `getMember` verifies an Auth user but does not check suspensions, and some other APIs use different authentication helpers. A modified client or a valid token can bypass this UI check. A recent non-suspended UI cache can also delay a later change for up to ten minutes, and network/server errors deliberately do not block the UI. Do not describe this as a suspension enforcement boundary.

Another consequential gap: the app shell signs out a suspended session, while the public `/appeal` screen and `/api/appeals` require an authenticated member. The current sign-in flow routes through onboarding/app instead of reliably sending an authenticated suspended member to an isolated appeal path. Therefore a suspended member may be unable to appeal or read the new system inbox. There is no safe basis to claim the requested suspension system message is accessible. Do not simply remove sign-out or unlock the full app to fix appeal access.

## Local mitigation, not a complete fix
The tab-local UI cache now accepts only a recent explicit non-suspension result scoped to the current account; old numeric values, other accounts, future/invalid entries and storage failures are cache misses. A suspended result clears the cache before sign-out, and storage write/read/remove failure cannot swallow the verdict. Successful password/OTP/signup entry and callback navigation invalidate the cache so a new login does not reuse an earlier same-account result. The cookie notice was updated. This changes neither the suspension policy nor API authorization and does not fix the appeal path. A previously valid same-session cache may still delay noticing a newly imposed suspension.

## Concurrent security-check writes — local checkpoint

A held-lock local test reproduced two simultaneous datacenter checks creating two active suspension rows and two audit events, and a forced suspension-insert error leaving a standalone audit event (`security-check-races-before.log`). The datacenter branch now serializes cooperating checks by normalized email, rechecks the latest suspension under that lock, and writes the event and suspension in one transaction. A failure returns a generic 503; a connection loss can leave the commit outcome uncertain. Local controlled tests (`security-check-races-after.log`) exercise two waiting handler calls and forced insert rollback. Existing latest-row selection is intentionally unchanged and multiple pre-existing rows are not repaired. The lock does not coordinate operator actions or any other writer unless they adopt it; it is not a uniqueness constraint, authorization gate, or proof that suspension/appeal access is safe. The existing UI treats errors as nonblocking, so a 503 is not fail-closed access control. Auth and IP reputation were simulated; no hosted account or data was changed.

## Required before claiming completion
Design and independently review a server-authoritative suspension policy across all authenticated API entry points, cached/live sessions and Realtime, with a narrow verified appeal/status channel that does not expose the normal app. Define source-of-truth identity and all suspension/lift workflows, avoid enumeration and private-reason leakage, decide safe event creation and an accessible notification route, and test suspended/unsuspended transitions, concurrent changes, appeal submission, outages, old tokens and real hosted behavior with controlled accounts. Do not infer authorization to mutate production or create hosted test infrastructure.

## Further source-level design hazards to resolve
- Suspension and appeal rows are keyed by lowercased email, not an immutable Auth UUID; `getMember` expressly acknowledges that a recreated Auth account can reuse an email from a legacy mirror. A new design must resolve verified ownership, email changes/reuse and historical records without disclosing another account's private appeal data. `/api/security/check` and appeal POST decide using the latest suspension row, while parts of `identity-resolve.ts` treat any active row as relevant. Multiple rows, case normalization, tie-breaking and operator lift workflows must be reconciled before treating a single predicate as authoritative; source inspection alone does not establish what data currently exists.
- `getMember` is shared by many APIs but is not the only auth path: onboarding, settings, profile-me and export also use `createSupabaseClientForApi` directly; Realtime and Storage may be accessed outside Next handlers. Blindly modifying `getMember` would both miss paths and interfere with appeals, human-challenge endpoints, support and account rights. Inventory each method and explicitly decide narrow allowed actions, authorization-failure semantics and behavior during DB/Auth outages. Provider tokens, existing sockets and signed/public media require separate handling.
- The local appeal challenge checkpoint below mitigates the reproduced replay, expiry, bookkeeping and duplicate-submission problems for participating HTTP handlers. The proof is limited to local tests; arbitrary external writers, suspension/lift and operator decision races still need separate review. Do not claim global single-use or server-wide enforcement based on these changes.

Consequently the earlier `appeal-challenge-browser-final.log` and the corresponding 320/1440 results from `reverify-appeal-auth-browser.log` did not establish that challenge requests actually carried browser authentication; the old fixture masked that omission. ## Challenge expiry under row-lock contention — local checkpoint

Controlled local database tests reproduced a separate expiry race in four paths: verification liveness and pose consumption, human challenge verification, and enforced appeal token consumption. With an unchanged challenge row locked by a concurrent transaction until after expiration, all four paths previously accepted the expired proof (`verification-consume-expiry-before.log`, `appeal-row-expiry-before.log`). A `clock_timestamp()` predicate on an UPDATE alone was insufficient in this scenario because its qualifying row had already been found before the lock wait. The earlier appeal test held the *advisory* lock, not the challenge row, and therefore did not cover this case.

These participating consumers now acquire the relevant row lock before their conditional, status- and expiry-checked writes; the expiry predicate uses PostgreSQL `clock_timestamp()`, not a transaction-start timestamp. Liveness and pose retain the former behavior for a legacy NULL expiry, although the declared schema requires non-NULL. The human verifier still has an earlier application-clock check that can reject early if application and database clocks disagree; the database predicate is the final guard against late acceptance. A pose that expires while waiting is refused, stored as expired, and recorded with the expired outcome. No claim is made for nonparticipating writers, clock integrity, hosted schemas or provider behavior.

Local disposable-DB checks cover the held-row-lock expiry races, parallel single-use, wrong-account and missing tokens, already-expired proofs, forced write rollback, and the existing issuance and appeal regressions (`consume-expiry-db-regressions.log`). Browser tests use synthetic Auth and local handlers (`consume-expiry-browser.log`). These tests do not establish hosted suspension/login, delivery or independent security review.
