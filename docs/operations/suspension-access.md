# Suspension notice and access: unresolved release gate

The current `/api/security/check` checks the latest suspension by email and returns a verdict; the app shell calls it asynchronously **after rendering** and normally signs the client out when `suspended` is true. It is not a server-wide authorization gate: `getMember` verifies an Auth user but does not check suspensions, and some other APIs use different authentication helpers. A modified client or a valid token can bypass this UI check. A recent non-suspended UI cache can also delay a later change for up to ten minutes, and network/server errors deliberately do not block the UI. Do not describe this as a suspension enforcement boundary.

Another consequential gap: the app shell signs out a suspended session, while the public `/appeal` screen and `/api/appeals` require an authenticated member. The current sign-in flow routes through onboarding/app instead of reliably sending an authenticated suspended member to an isolated appeal path. Therefore a suspended member may be unable to appeal or read the new system inbox. There is no safe basis to claim the requested suspension system message is accessible. Do not simply remove sign-out or unlock the full app to fix appeal access.

## Local mitigation, not a complete fix
The tab-local UI cache now accepts only a recent explicit non-suspension result scoped to the current account; old numeric values, other accounts, future/invalid entries and storage failures are cache misses. A suspended result clears the cache before sign-out, and storage write/read/remove failure cannot swallow the verdict. Successful password/OTP/signup entry and callback navigation invalidate the cache so a new login does not reuse an earlier same-account result. The cookie notice was updated. This changes neither the suspension policy nor API authorization and does not fix the appeal path. A previously valid same-session cache may still delay noticing a newly imposed suspension.

## Required before claiming completion
Design and independently review a server-authoritative suspension policy across all authenticated API entry points, cached/live sessions and Realtime, with a narrow verified appeal/status channel that does not expose the normal app. Define source-of-truth identity and all suspension/lift workflows, avoid enumeration and private-reason leakage, decide safe event creation and an accessible notification route, and test suspended/unsuspended transitions, concurrent changes, appeal submission, outages, old tokens and real hosted behavior with controlled accounts. Do not infer authorization to mutate production or create hosted test infrastructure.

## Signed-out appeal guidance (local only)
The public `/appeal` page now stays visible when no session is found instead of silently redirecting to sign-in. It explains that the form requires a session, that sign-in may not return to the page, and offers a user-initiated email link to the published support address without claiming email delivery or a response. Session/API load errors retain a retry and the same fallback. The auth status link now points to appeal *information*, not an assertion that the form is available. This does not send email, change authentication, exempt suspended accounts from restrictions, or make the authenticated appeal form reachable after sign-out. A link or mailbox is not evidence that an appeal was filed or that support received it.

## Further source-level design hazards to resolve
- Suspension and appeal rows are keyed by lowercased email, not an immutable Auth UUID; `getMember` expressly acknowledges that a recreated Auth account can reuse an email from a legacy mirror. A new design must resolve verified ownership, email changes/reuse and historical records without disclosing another account's private appeal data. `/api/security/check` and appeal POST decide using the latest suspension row, while parts of `identity-resolve.ts` treat any active row as relevant. Multiple rows, case normalization, tie-breaking and operator lift workflows must be reconciled before treating a single predicate as authoritative; source inspection alone does not establish what data currently exists.
- `getMember` is shared by many APIs but is not the only auth path: onboarding, settings, profile-me and export also use `createSupabaseClientForApi` directly; Realtime and Storage may be accessed outside Next handlers. Blindly modifying `getMember` would both miss paths and interfere with appeals, human-challenge endpoints, support and account rights. Inventory each method and explicitly decide narrow allowed actions, authorization-failure semantics and behavior during DB/Auth outages. Provider tokens, existing sockets and signed/public media require separate handling.
- The local appeal challenge checkpoint below mitigates the reproduced replay, expiry, bookkeeping and duplicate-submission problems for participating HTTP handlers. The proof is limited to local tests; human-challenge issuance concurrency, arbitrary external writers, suspension/lift and operator decision races still need separate review. Do not claim global single-use or server-wide enforcement based on these changes.

## Appeal challenge and concurrent filing — local checkpoint

Reproduced locally: the verify endpoint accepted a challenge in `failed` state again, an expired solved token authorized an appeal, and non-string detail threw instead of returning 400 (`appeal-challenge-before.log`). The earlier `failed` state was also used to mark an appeal token consumed; re-verification could therefore resurrect it. No live account, provider or hosted database was touched.

Local implementation uses an atomic issued/unexpired/attempt-limited transition for verification; failed and expired are terminal for this HTTP verifier. Appeal POST serializes its own submissions per normalized email and combines the pending check, conditional one-use unexpired token consumption and insert in one transaction. The consumed token becomes terminal `expired` using the existing status vocabulary; insert failure rolls consumption back. Enforced mode does not silently bypass a failed challenge bookkeeping query; a database error returns an uncertain-submission 503, and client transport failures advise checking status before retry. Record mode remains record-only, with its missing-challenge event written transactionally. Invalid detail is rejected and a decided non-cleared appeal offers a new form; server remains authoritative on eligibility.

No actual suspended sign-in, live review, mail or provider acceptance. See `appeal-challenge-regressions.log` and build/checks/trust logs.

The lock serializes only this route's cooperating submissions, not operator SQL, suspension changes, direct DB writers or other services. Existing email-identity, latest-row semantics, route reachability and cross-service suspension gaps remain. An uncertain commit cannot always be distinguished from a rollback after connection loss; checking status before retry remains necessary. No production configuration flag or schema was changed, and this is not permission to enable enforcement or declare the appeal/suspension release blocker closed.

## Appeal challenge issuance and browser authentication — local follow-up

A corrected local browser fixture no longer injects a member identity into every request. It substitutes a synthetic identity only when the actual browser request contains the exact fixture Bearer token. With the prior client, appeal GET/POST carried the token, but challenge issuance did not: the real local handler returned 401 (`appeal-bearer-before.log`). Consequently the earlier `appeal-challenge-browser-final.log` and the corresponding 320/1440 results from `reverify-appeal-auth-browser.log` did not establish that challenge requests actually carried browser authentication; the old fixture masked that omission. The SPA normally stores its session in localStorage, so an SSR cookie cannot be assumed. The client now passes the same access token used by the appeal POST to both issue and verify requests; cookie fallback remains possible if no token was obtained. Token expiry, auth refresh and account switching during a long check are not comprehensively tested.

Controlled concurrent real-handler tests reproduced a partial-unique-index violation when two issuers both expired before either inserted, and a fault-injected insert that left the old challenge expired (`issue-races-before-controlled.log`). The issue endpoint now takes a transaction-scoped per-normalized-email-and-purpose advisory lock, expires issued rows and inserts the new row atomically. Local tests (`issue-races-final.log`, six checks) cover held-lock concurrency, rollback on forced insert failure, member/purpose separation, superseded verification, preservation of an already solved token and request guards. A 503 does not assert whether a commit happened. This serializes cooperating `/api/human/issue` calls only; the partial unique index remains the backstop, an already returned nonce may be superseded by a later issuance, solved rows are not revoked by new issuance, and it is not an issuance rate limit. Other writers do not necessarily share the lock.

The corrected local Chromium fixture (`appeal-issue-browser-final.log`) asserts that both issue and verify requests actually carry the synthetic bearer, uses real local challenge and appeal handlers, forces an insert failure, supersedes an issued nonce, checks that both failures retain the appeal draft, and retries to file one synthetic appeal at 320 and 1440px. `appeal-issue-checks.log` includes the 16 existing appeal DB checks, 625/625 trust assertions, typecheck/lint/manifest/secret checks; `appeal-issue-browser-regressions.log` covers related local guidance, security, auth, verification, settings and inbox browsers. The 320px error screenshot was inspected. Auth itself remains substituted; no hosted provider, actually suspended sign-in, support delivery or independent review was performed. This does not resolve the signed-out appeal access or global suspension authorization blocker.

The separate `/api/verification/challenge` issuer has analogous nontransactional expire-then-insert code. A controlled disposable-DB test (`verification-issue-investigation.log`) observed one handler exception under concurrent issuance and expiration of the previous token when an insertion was forced to fail. It also assigns poses in separate database operations, so its ordering with concurrent issuance needs careful review; the present appeal fix does not cover it. The reproduced verification-issuance defects remain open pending a separately tested fix. No production change was made.
