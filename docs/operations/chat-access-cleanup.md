# Open chat access cleanup: local checkpoint

## Scope and limits
This change is a **compliant-client cleanup**, not a server-side Realtime security fix. After a tagged, definitive conversation denial, an open thread hides its prior messages and controls, closes open media/voice/call overlays, stops pending typing hints, and offers retry/back. A readable-but-unwritable thread continues to display history for reporting, hides the composer, and closes an active voice-note recorder (discarding its unsent recording). The typed text draft is retained in memory and reappears if access is restored without leaving the thread. Already delivered/saved content cannot be recalled.

The messages GET handler tags its own conversation-level 403/404 responses with `code: "thread_unavailable"`; it does not tag an unrelated origin-guard refusal. Transient failures, 401s, and untagged errors do not masquerade as confirmed loss of access or erase the visible thread. A later successfully authorized response can restore the view. Sequencing prevents an older-started response that arrives late from overwriting a newer applied response; it does not make request start order equivalent to database commit order, and only a fresh server decision can establish current access. The UI retains HTTP polling/visibility recovery, subject to its existing offline/background and scheduling limits.

This does **not** revoke a modified client's cached Supabase socket, stop arbitrary Broadcast payloads, establish global or immediate revocation, validate public Realtime settings, or enforce lifecycle rules on independently accessible channels. Production Realtime authorization and socket revocation remain an open release blocker. A call overlay uses its own session-based revocation for a read-only participant; when the conversation itself becomes unavailable the overlay is unmounted and releases local media. An already disconnected or modified peer and issued TURN credentials retain their previously documented limitations.

## Compatibility and release gate
Ship the GET response marker before or together with the client. During a mixed deployment, an old server's untagged 403/404 will be treated as an ordinary fetch failure by the new client, so immediate cleanup cannot be assumed until every serving instance has the new API. No migration is introduced by this change. Do not deploy without approval, an independent security/code review, verified Realtime mitigation, and controlled hosted two-member acceptance (including an old tab, network failure and simultaneous requests). Rollback the client/API together; do not weaken the existing HTTP authorization.
