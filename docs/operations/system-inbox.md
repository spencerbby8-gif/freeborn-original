# Freeborn updates: local checkpoint

## Design
A fixed Freeborn-branded row in the Messages inbox links to `/app/chat/freeborn`. Its mark is decorative and not a profile control. This is not a member account or match, and has no send, call or typing controls. It reads existing account-owned `member_notices` (welcome, verification, appeal verdict and support reply where the existing triggers created them); it creates no member messages and sends no email. The welcome notice is generated by the existing first-onboarding-completion trigger, with no historical backfill. The inbox includes a static link to safety guidance on scams, credentials, blackmail, reporting and safer meetings; this is educational content, not a newly delivered event.

Each notice can be explicitly marked read; opening its related page marks it first. Marking is owner-scoped and idempotent. Unsafe/non-app hrefs do not render a navigation action. The first page and older pages use `(created_at,id)` keyset ordering with microsecond precision; unread count covers all notices, not only the first page. Refresh reloads from the newest page. Concurrent inserts or reads may be reflected on the next refresh rather than atomically in every counter.

Notifications and Messages point to the **same notice records**, rather than creating duplicate records or a fake chat. Durable unread system notices remain visible after feed clear; clear does not mark them read. Both navigation badges include the server unread system count plus their existing respective non-system counts, so one unread system item can be indicated in both navigation locations, not counted twice within either number. The notification feed continues to show at most 50 latest durable notices, while the inbox offers older pages. System notices do not generate the existing social sound/banner pipeline; there is no push or cross-device instant-update guarantee. A manual refresh or the existing foreground poll reconciles state. New entries inserted with an old sort timestamp after a page was loaded may need refresh to appear.

## Critical limits
No suspension notice is fabricated. The current security check signs suspended users out of the authenticated app, and an accessible, verified suspension/appeal notice and enforcement across API paths have not been designed or tested. Do not claim a suspended account can reach this inbox. Existing trigger coverage does not establish every possible administrative suspension or decision. Some real account safety events and provider delivery remain unverified. Production Realtime authorization and old-socket revocation remain release blockers; this UI is not a fix. No migration added by this checkpoint, and no hosted test or deployment was performed.
