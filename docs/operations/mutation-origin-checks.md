# Browser-origin checks — local checkpoint, not hosted acceptance

The signed-in security-check POST can create security events and an active suspension. A disposable-PostgreSQL test using the real handler, a synthetic authenticated identity and a simulated datacenter reputation response showed that a request with a foreign `Origin` could create both (`security-check-before-mutation.log`). This does not establish that a production browser sent credentials cross-site: that depends on deployed cookie, CORS, proxy and browser settings. The endpoint now calls the shared `rejectCrossOrigin` before Auth, provider lookup or writes; the local before/after test covers a foreign origin, a same-origin synthetic suspension, preexisting suspension, anonymous requests and the existing no-Origin behavior (`security-check-origin-after.log`). No real member, reputation service or hosted database was contacted.

A separate local inventory found eight more function-form mutation handlers without the common guard: verification submission and check, heartbeat, onboarding patch, profile update, call trace, event interest and the callback exchange. Each now applies the same guard at the top of its POST. Synthetic local tests send JSON as `text/plain` with a foreign Origin and verify 403, exercise same-origin handling and the existing no-Origin allowance, and demonstrate that cross-origin event interest cannot write while same-origin writes the disposable DB; profile changes use a substituted auth/data adapter (`mutation-origins-after.log`, `origin-filter-db-final.log`). The source-only inventory covers 38 function-form handlers; it explicitly excludes the secret-authenticated scheduler and signature-verified email webhook. It does not prove behavior of alternate export forms or deployed proxies.

The shared guard intentionally permits a missing Origin and configured allowed origins, including same-host fallback. This is a defense against a *present foreign Origin*, not authentication, a general CSRF proof or a suspension-authorization boundary. Same-origin XSS, stolen tokens, origin/host and proxy configuration, actual cookie behavior, direct Supabase paths and hosted clients remain outside these tests. Before release independently review the policy and deployed allowed-origin configuration, and test real Auth/PKCE with controlled accounts. The IP reputation flow and suspension policy themselves are unchanged, including the documented external IP disclosure and fail-open behavior. Machine endpoints must retain their own authentication/signature verification.

## Wrapped location writer follow-up

The first inventory above only covered `export function` syntax and missed the location writer because it is exported through `withMemberApiErrors`. A separate local test (`location-origin-before-write.log`) confirmed that a foreign-Origin, `text/plain` request could save synthetic coordinates in the disposable database. The guard now runs at the start of the wrapped `saveLocation` handler; `location-origin-after.log` verifies foreign denial and a valid same-origin write, and the existing 19-case member-runtime suite still passes (`location-origin-member.log`). This does not prove an actual hosted cross-site cookie exploit.

The inventory now uses the TypeScript parser to follow the function, inline-arrow and wrapper forms found here: it checks 49 browser mutation handlers, with three explicit exceptions: secret-authenticated email dispatch, signature-verified inbound webhook, and the one-click unsubscribe endpoint whose URL token is the authorization. This remains a source check, not proof of runtime behavior, arbitrary dynamic re-exports, or deployed configuration. Do not add an Origin requirement to the one-click or webhook paths without checking their external-client contracts.
